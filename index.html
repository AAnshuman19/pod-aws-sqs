Notes

What this simulation simplifies
  • Time advances in 0.25 s steps from a fixed seed, so the same settings give the same result. Nothing here is AWS telemetry.
  • One standard queue, one message at a time per pod (round 4 batches 10). Real SQS also has long polling, delay queues, FIFO ordering and per-request pricing.
  • A message received by a pod stays hidden until the visibility timeout. A late delete is accepted only if no other pod holds the message. Real SQS treats stale receipt handles less predictably, which is one more reason to be idempotent.
  • KEDA and HPA are collapsed into one loop: each polling interval it reads visible plus in-flight messages, divides by queueLength, and adds at most max(4, current) pods per interval. Scale-in waits for the cooldown. Real HPA has its own sync period and stabilization windows.
  • Costs use a made-up rate of $1.20 per pod-hour so you can compare choices. They are not AWS prices.

How it works for real

This game is a simulation. It does not create, read or change any AWS resource and needs no credentials. The configuration below shows how the same ideas look on a real EKS cluster. Every account ID, region, queue URL, role ARN and cluster name is a placeholder in angle brackets. Never commit real credentials, and check each snippet against the versions of EKS, KEDA and the AWS CLI you run.

1Architecture

Producers write to SQS. KEDA watches the queue length and drives a Horizontal Pod Autoscaler, which resizes the worker Deployment. Workers pull messages themselves; SQS never pushes.

2The message lifecycle

  1. A producer calls SendMessage. The message is stored on several servers and counts as visible.
  2. A worker calls ReceiveMessage (use long polling, WaitTimeSeconds=20). SQS returns up to 10 messages and starts the visibility timeout. Each message gets a fresh receipt handle and its receive count goes up by one.
  3. While hidden, the message is "in flight". Other workers cannot receive it.
  4. On success the worker calls DeleteMessage with the latest receipt handle. The message is gone.
  5. On crash, error, or a job that outlives the timeout, nothing deletes it. The timeout expires and the message becomes visible again.
  6. If you configured a redrive policy and the receive count reaches maxReceiveCount, SQS moves the message to the dead-letter queue instead of delivering it again.

That loop is why standard queues are at-least-once: step 5 can run after the side effect in step 3 already happened.

3Worker Deployment

The workers are an ordinary Deployment. They get AWS access from their service account, not from keys in environment variables. The replica count is owned by the autoscaler, so leave replicas out once KEDA manages it.

4KEDA ScaledObject for SQS

    
This is round 4 as YAML. KEDA computes ceil((visible + in flight) / queueLength), clamps it between the min and max replica counts, and hands the number to an HPA it creates for you. queueLength is the backlog per replica you want to tolerate. It is not how fast a pod works, so size it from your measured throughput per pod.

cooldownPeriod only governs the last step down to zero. For scaling between 1 and N, the HPA's own stabilization window applies. Set minReplicaCount: 0 only if your users can wait for a cold start of a new pod.

7Redrive policy and dead-letter queue

    
Create the DLQ first, give it a longer retention than the source queue (14 days is the maximum), then point the source queue at it. Standard queues need a standard DLQ.

    
dead-letter queue setup

    
Pick maxReceiveCount above the number of times a healthy message might fail from throttling or a brief outage. Three to five is common. After you fix the bug, move the messages back with a redrive task and alarm on the DLQ depth so nobody forgets them.

  


  

    
8Visibility timeout and idempotency

    
    
      
  • Set the visibility timeout a little above your slowest normal job (p99 plus margin). Too short makes duplicates, too long delays recovery after a crash.
    • 
      
  • For long or variable jobs, start with a modest timeout and call ChangeMessageVisibility while working to extend it.
    • 
      
  • Handle SIGTERM: stop polling, finish the in-flight message, then exit. Set terminationGracePeriodSeconds above your job time.
    • 
      
  • Assume every message can arrive twice. Key the side effect on a business ID such as the order ID and make the write conditional.

10Production considerations

    
    
      
  • Monitoring. Alarm on ApproximateAgeOfOldestMessage (users feel latency here), DLQ depth above zero, pod restarts, and worker error rate. Queue depth alone hides slow consumers.
    • 
      
  • Downstream limits. Autoscaling workers can overload a database or a partner API, as in round 1. Cap maxReplicaCount to what the dependency can take and add backoff.
    • 
      
  • Nodes. Pods need somewhere to run. Pair KEDA with Karpenter or Cluster Autoscaler and keep spare capacity for bursts, or pods sit Pending as in round 4.
    • 
      
  • Disruptions. Use a PodDisruptionBudget and graceful shutdown so node upgrades do not abandon messages mid-job.
    • 
      
  • Ordering. Standard queues give no ordering guarantee. If you need it, use FIFO queues with message group IDs, and accept lower parallelism.
    • 
      
  • Cost. Long polling and batching (up to 10 messages per call) cut SQS request charges. Scale to zero saves compute but adds cold-start latency.
    • 
      
  • Failure drills. Kill pods during a load test, revoke the KEDA permission in a test account, and send a deliberate poison message. Watch what your dashboards and alarms show before real traffic does it for you.
